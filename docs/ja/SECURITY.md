# セキュリティ

[English](../../SECURITY.md)

KeyRelay はハードウェアのセキュリティキーを Bluetooth LE で中継します。これはキーの前提
（パソコンに直接挿して使う）を意図的に変えるものなので、頼る前に読んでください。

## 脆弱性の報告

このリポジトリの **Security → Report a vulnerability**（GitHub の非公開の脆弱性報告）から
知らせてください。公開の Issue には書かないでください。趣味のプロジェクトなので、返事には
2週間ほどかかることがあります。

## 何をしているか

```
パソコン ──USB── レシーバー（ESP32-S3） ── BLE ── 机上ユニット（ESP32-S3、USB ホスト） ──USB── セキュリティキー
```

レシーバーはパソコンから、FIDO HID・CCID スマートカードリーダー・OTP キーボードに見えます。
メッセージはそのまま机上ユニットのキーに届け、応答もそのまま返します。例外は1つで、机上ユニットは
CTAPHID のチャンネル ID を仮想化します（パソコンのブロードキャスト `CTAPHID_INIT` には自分で答え、
FIDO パケットごとに先頭4バイトのチャンネル ID を書き換える）。キーが再列挙されてもチャンネルが
切れないようにするためです。CTAP のコマンド・APDU・OTP のフレームは、分割と組み立てに必要な分しか
読みません。

**秘密鍵はキーの外に出ません。** FIDO の資格情報、PIV / OpenPGP の秘密鍵、OATH のシード、
チャレンジレスポンスの HMAC 鍵は、直接挿したときと同じくキーの中にあります。
**本人確認は、机上ユニットにあるキーへのタッチのまま**です。

## BLE の守り方

2つの層があります。

1. **BLE の LE Secure Connections**（ECDH、Just Works、ボンディング）。机上ユニットが*新しい*
   ペアリングを受け付けるのは、まだ相手がいないときか、起動後120秒の間だけです。Just Works は
   ペアリングの瞬間の中間者攻撃を防げないので、2つ目の層があります。レシーバーが机上ユニットを
   「登録済みの相手」として覚えるのは、2つ目の層の相互認証が通ってからです。また、この接続で新しく
   ペアリングしたのに相互認証を終えなかった相手（理由を問わず。自分から切った場合も）と、相互認証で PSK が
   違うと分かった相手の BLE ペアリング情報は、2台とも消します。この接続より前からあったペアリング情報は、
   相互認証が時間切れになったり、ほかの理由で失敗したりしただけなら残します。その情報で暗号化できた相手は、
   それを作った本物の相手だからです。レシーバーは、登録済みの机上ユニットとの暗号化に失敗しても、その
   ペアリング情報を消さず、ペアリングし直しもしません。鍵を持たない機器でも、机上ユニットのアドレスを
   名乗って、わざと暗号化を失敗させられるからです。机上ユニットは、すでにペアリング情報のある相手が
   ペアリングし直そうとするのを、起動後120秒の受付時間の間だけ受け付け（ペアリング情報をなくした
   レシーバーなど）、受付時間の外では断ります。受け付けるときは、古いペアリング情報を消す前に RAM に
   控えておき、ペアリングし直した相手がその接続で相互認証を通らなければ書き戻します。そのため、受付時間中に
   レシーバーのアドレスを名乗っても、そのペアリング情報を置き換えることはできません。同じ接続の中での
   2回目のペアリングのし直しは断ります。控えは RAM にしかないので、ペアリングのし直しを受け付けたあと、
   その相手が相互認証を終える前に机上ユニットの電源が切れると、前のペアリング情報は書き戻されません。
   そのときは、本物のレシーバーの BOOT を3秒押してペアリングし直すまで、つながりません。
   ペアリング情報の保存先がいっぱいになっても、古い相手を消して場所を空けることはしません。そのため、
   鍵を持たない機器が、レシーバーに自分を覚えさせたり、机上ユニットのペアリングの枠を取り続けたり、
   正規の相手を追い出したりすることはできません。
2. **事前共有鍵（PSK）と使い捨ての X25519 によるアプリ層の暗号化**（リンクの版 v2）
   （[`firmware/components/yd_link/yd_sec.c`](../../firmware/components/yd_link/yd_sec.c)）:
   - 2台に同じ 256bit の乱数の鍵を書き込みます（`0x190000` の `ydkey` パーティションに
     `YDK1` ＋ 32バイト）。正しい鍵がなければ BLE は動きません。
   - 2台は、決まった目印なしに相手を見つけます。机上ユニットは名前をアドバタイズせず、GATT のサービスと
     キャラクタリスティックの UUID は PSK から作ります（それぞれ `HMAC-SHA256(PSK, "keyrelay v2 gatt uuid" ‖ n)`、
     n = 0・1・2 の先頭16バイトなので、3つの間に見て分かる関係はありません）。スキャンしても、よく知られた UUID や
     名前で KeyRelay だと見分けることはできず、レシーバーは別の PSK で設定した机上ユニットを相手にしません。
     2台とも起動時に、サービスの UUID の先頭4バイトを `Link ID`（日本語のログでは「リンク ID」）としてログに
     出します。2台で同じになるはずです。登録済みの机上ユニットや古いファームの机上ユニットが別のものを
     アドバタイズしていれば、レシーバーがログで知らせます。
   - 接続のたびに、両方が16バイトの乱数と、その接続のために作った X25519 の公開鍵を送り合います。
     X25519 の秘密鍵は RAM にしか置かず、鍵を作ったらすぐ消します。この接続だけの鍵（方向ごとに
     1つずつと、認証用）は HKDF-SHA256 で作り、材料は PSK と X25519 の共有値、ソルトは2つの乱数と
     2つの公開鍵です。共有値が 0 になる公開鍵（小さい位数の点）は受け付けません。接続ごとの鍵は
     どこにも保存しなかった値に依存するので、あとで PSK と BLE のボンド情報を機器から読み出されても、
     録られていた通信は復号できません（前方秘匿性。Noise の `NNpsk0` や TLS 1.3 の `psk_dhe_ke` と
     同じ考え方）。
   - 相互認証: 互いに `HMAC-SHA256(k_auth, "YD-AUTH" ‖ 役割 ‖ 乱数)` の先頭16バイトを送り、
     定数時間で比べます。違ったときと、BLE の暗号化が済んでから5秒以内に終わらないときは切断します。
     また、接続してから15秒以内に相互認証まで終わらない接続も切ります（暗号化や通知の購読をしない
     相手など）。それでも、つなぎ直しを繰り返す相手は、1つしかない接続枠をほとんどの時間ふさげます
     （電波の妨害と同じ、サービス妨害です）。
   - データ: パケットごとに AES-256-GCM。5バイトのヘッダー（種別＋32bit の通し番号）も
     改ざん検知の対象（AAD）で、通し番号が IV になります。通し番号はちょうど1ずつ増えないと受け付けない
     ので、再送・並べ替え・一部だけの抜き取りはどれも検出して接続を切ります。一周する前にリンクを切ります。
   - 暗号化の前に、どのパケットも 32バイトの倍数まで埋めます（`0x80` のあと `0x00`。1パケットに入る最大の
     大きさのほうが小さいときは、そこまで）。そのため、パケットの大きさから PIN の桁数（OpenPGP は PIN を
     埋めずに送ります）は分かりません。タッチ1回分のキー入力は、
     打たれた中身にかかわらず、同じ大きさのパケットを 50ms ごとに少なくとも2秒間送る決まった並びで送ります。
     パケットの大きさからも時刻からも、打たれた OTP や静的パスワードの長さは分かりません。
   - 2台は同じ版のリンクで動かす必要があります。版が違う相手とは、ログに出して切断します。
     2台はいっしょに更新してください。

**鍵を持たない**電波の届く範囲の攻撃者は、妨害や切断（サービス妨害）はできますが、
中継されるメッセージを読んだり、差し込んだり、再送したり、選んで抜き取ったりはできません。

## PSK が漏れたら

PSK は全部の機器（机上ユニットとそれぞれのレシーバー）で共有する対称鍵です。現実に漏れるのは、どれかの
機器のフラッシュを読み出されたとき（フラッシュ暗号化は既定でオフ）か、パソコンに残った `keyrelay-key.bin`
のコピーからです。
フラッシュを読み出されると BLE のボンド情報（LTK）も一緒に取られるので、BLE の暗号化は守りになりません。

- **過去の通信は守られます。** 前の接続の録音は、PSK とボンド情報があっても復号できません。
  その接続の X25519 の秘密値は、どこにも保存していないからです（上記）。
- **机上ユニットになりすます（こちらのほうが深刻です）。** PSK があれば、偽の机上ユニットが本物の
  レシーバーにつながれます。レシーバーはパソコンから見ると USB キーボードなので、偽の机上ユニットは
  **タッチも PIN もなしに、キー入力を打たせられます**。既定では、レシーバーは Yubico OTP の形をした入力しか
  打ちません（`CONFIG_YD_OTP_KBD_FILTER_MODHEX`）。ひと続きのキー入力の中で、修飾キーなしの ModHex（16種類の文字）を
  64文字まで、Enter はその文字が 32〜64文字打たれた直後だけです（OTP 1つにつき Enter 1回。「OTP と Enter」が
  ひと続きの中で続けて来ることはあります）。それ以外のものが来たら、そのひと続きの
  残りは打ちません。1つのレポートに入れてよいキーは1つだけで、通したキーはレシーバー自身が「押す」「離す」に
  して打つので、キーを押しっぱなしにしてパソコンのキーリピートで文字を増やすこともできません。
  そのため偽の机上ユニットは、コマンドも、ほかの文字も、短い返事と Enter も打てません。
  打てるのは ModHex の文字と、32文字のあとの Enter です。1文字のショートカットを持つアプリ（vim や一部の
  Web アプリ）やダイアログの既定のボタンは、それに反応します。OTP をうっかり違う場所で打ったときと同じです。
  静的パスワードのために「Any key」を選んだときは、下の「キー入力の差し込み」を読んでください。OTP を使わない
  なら、レシーバーを `CONFIG_YD_OTP_KEYBOARD=n` でビルドすれば、キーボードそのものがなくなります。
  偽の机上ユニットは、スマートカードや FIDO の要求に自分で答えることもできますが、あなたのキーの署名や
  アサーションは作れません。
- **レシーバーになりすます。** 偽のレシーバーは、電波の届く範囲からキーと通信できます。たいていの操作には
  PIN とタッチが要りますが、要らないものもあります。
  - OATH（TOTP / HOTP）のコードは、OATH のパスワードを設定し、アカウントにタッチを必須にしていなければ、
    タッチも PIN もなしで計算できます（`ykman oath access change`、`ykman oath accounts add --touch`）。
  - OTP のチャレンジレスポンス（HMAC-SHA1。KeePassXC が使う）は、スロットを `--touch` 付きで設定して
    いなければ、タッチなしで答えます。
  - PIN をわざと間違え続けて試行回数を使い切り、PIV / OpenPGP の PIN をロックすることはできます
    （サービス妨害）。
  - **タッチなしで、キーの設定を壊すこともできます**（秘密を盗むのではなく、サービス妨害です）。
    机上ユニットが APDU を読まずに中継するスマートカードの口からは、OATH のリセット、PIN と PUK を
    使い切ってからの PIV・OpenPGP のリセット、管理用のアプリケーションでの設定の変更（使える口、設定の
    ロックコード）ができます。OTP については、キーを書き換えるコマンド（スロットの書き込み・更新・入れ替え・
    削除、アクセスコード、NDEF、デバイスの設定）を机上ユニットが止めます。通すのはチャレンジレスポンスと、
    シリアル番号・機能の読み出しだけです。そのため KeyRelay 越しにはスロットを設定できません。スロットの設定は
    キーをパソコンに直接挿して行ってください。
- **気づけないことがあります。** キーを盗まれればすぐ気づきますが、PSK を黙ってコピーされても
  気づけません。漏れた疑いがあれば、鍵ファイルを作り直して全部の機器に書き込み、BLE のペアリング情報を
  消してください。

根本的な対策は、PSK を読み出されないようにすることです。[HARDENING.md](HARDENING.md) を
見てください。机の上に出ている机上ユニットから先に固めるのがおすすめです。

## 機器をなくしたり、盗まれたりしたら

人の手に渡った機器も、守りを固めてあってもなくても、KeyRelay の機器としてそのまま動きます。
ほかの機器と通信するのに、フラッシュから何かを読み出す必要はありません。

- **レシーバー。** PSK と、机上ユニットとのボンド情報を持っているので、電波の届く範囲から、あなたの
  レシーバーと同じようにキーを使えます（上の「レシーバーになりすます」）。机上ユニットのペアリング情報を
  消しても（BOOT を3秒）、締め出せ**ません**。ペアリング相手のいない机上ユニットは新しいペアリングを
  受け付け、なくしたレシーバーは PSK を持っているので相互認証を通れるからです。
- **机上ユニット。** セキュリティキーが挿さっていたなら、まずキーをなくしたときと同じ対処をしてください。
  机上ユニット自体も PSK とそれぞれのレシーバーとのボンド情報を持っているので、レシーバーに対して
  机上ユニットになりすませます（上の「机上ユニットになりすます」）。

どちらの場合も、新しい PSK を作って手元に残った全部の機器に書き込み、BLE のペアリング情報を消してください。
古い PSK の機器は、もうほかの機器を見つけることも、相互認証を通ることもできません。

これは設計によるものです。全部の機器で1つの PSK を共有しているので、機器を締め出す方法は PSK を変える
ことだけで、そのたびにほかの全部の機器を書き換えることになります。機器ごとの鍵（それぞれが自分の鍵ペアを
持ち、机上ユニットが受け入れるレシーバーの一覧を持つ。Noise の `KK` のような形）にすれば、ほかに手を
付けずにレシーバーを1台だけ外せます。リンクの新しい版が必要になり、まだ実装していません。

## 守れないもの

- **中継機はパソコンが送ったものを平文で見ます。** PIV の PIN、OpenPGP の PIN と管理者 PIN、
  PIV の管理キー、OATH のコード、打たれた OTP、チャレンジレスポンスの入出力も含みます。例外は
  FIDO2 の PIN で、CTAP2 の PIN/UV 認証プロトコルにより、中継機の知らない鍵でパソコンとキーの間で
  暗号化されます（U2F には PIN がありません）。2台とも信用できるコードで動かす必要があります。
  自分でビルドしたか、確かめたファームだけを書き込んでください。
- **キー入力の差し込み。** パソコンから見ると、レシーバーは USB キーボードです（OTP を打つため）。
  書き換えられたファームや、すり替えられたそっくりなレシーバーは、悪意のある USB キーボードと
  同じように、好きなキー入力を打ち込めます。PSK を持つ偽の机上ユニットも、本物のレシーバーに
  打たせられます。既定のフィルターで、打てるのは Yubico OTP の形をした入力だけになっています
  （「PSK が漏れたら」参照）。静的パスワードや OATH-HOTP の数字を打つスロットがあるときは「Any key」
  （`CONFIG_YD_OTP_KBD_FILTER_NONE`）を選ぶ必要があり、その制限はなくなります。OTP を使わないなら、
  レシーバーを `CONFIG_YD_OTP_KEYBOARD=n`（menuconfig → KeyRelay）でビルドしてください。キーボードの口
  そのものがなくなります。
- **タッチは、そのとき来ている要求を何でも承認します。** タッチが証明するのは「机上ユニットのそばに
  人がいる」ことで、「その要求が自分の意図したアプリから来た」ことではありません。パソコンが
  乗っ取られていると、身に覚えのない要求でキーが点滅することがあります。そのときは触らないで
  ください。FIDO2 / WebAuthn はサイト（RP ID）と結び付けられたままですが、PIV・OpenPGP・OTP には
  その仕組みがなく、PIV / OpenPGP の多くの操作は既定では PIN だけで済みます。キーのタッチポリシーを
  検討してください（PIV は鍵を生成・インポートするときの `--touch-policy`、OpenPGP は
  `ykman openpgp keys set-touch`）。
- **どちらかの機器を物理的に手に入れられること。** 既定ではフラッシュ暗号化とセキュアブートを
  有効にしていないので、数分機器を借りられれば、PSK と BLE のボンド情報を読み出し、どちらの機器にも
  なりすませます（「PSK が漏れたら」参照）。机上ユニットは、キーそのものと同じように扱ってください。
  [HARDENING.md](HARDENING.md) の手順で、フラッシュ暗号化（Release モード）・セキュアブート v2・NVS 暗号化・
  セキュアダウンロードモードを有効にできます。2台ともビルドできる設定と、署名・暗号化のスクリプトも
  用意してあります。レシーバーの実機で確かめました（机上ユニットはまだ）。eFuse の操作はどれも元に戻せない
  ので、必ず予備の基板で先に試してください。守りを固めると PSK は読み出せなくなりますが、盗まれた機器を
  そのまま使われることは防げません（「機器をなくしたり、盗まれたりしたら」参照）。また ESP32-S3 は、基板を
  開けてのフォールト注入には耐えられません（HARDENING.md 参照）。
- **機器のメモリーにある平文。** リンクの層は、暗号化の元と復号の先のバッファーを消します。ただ、送信キューと、
  PIN や APDU が通る USB や組み立て用のバッファーは、次に使われるまで中身が残ります。RAM を読むにはデバッガー（JTAG。
  守りを固めると使えなくなる）か、チップへの物理的な攻撃が必要です。
- **机上ユニットのシリアル（ログ）経由の書き換えを有効にした場合。** `firmware/desk_unit/main/main.c`
  の `YD_UART_DOWNLOAD_CMD` を `1` にすると（既定は `0`）、机上ユニットの USB-UART に
  `keyrelay-download` の1行を送ったとき ROM のブートローダーで再起動し、ケースを開けずに書き換え
  られます。その USB-C をパソコンにつないでいる間は、**そのパソコンで動くどのソフトでも**、書き換えや
  フラッシュ（PSK を含む）の読み出しができます。有効にするなら、普段は充電器から給電してください。
  守りを固めた機器（セキュアダウンロードモード）なら、危険はずっと小さくなります。パソコンのソフトは
  フラッシュを読めず、書いたものもあなたの鍵で署名・暗号化していなければ起動しないからです。
- **レシーバーの UART（COM）側。** 一般的な ESP32-S3 開発ボードでは、この口からブートローダーに
  リセットできます。普段は挿さず、ネイティブ USB 側だけをつないでください。
- **中継の距離。** WebAuthn は、認証器がパソコンのすぐそばにあることを前提にしています。KeyRelay は
  わざとそれを BLE の届く範囲まで広げます。遠くの攻撃者がキーを使えないのは、机上ユニットのキーに
  誰かが触れる必要があるからです。
- **電波から分かること。** 埋め草で正確な長さは隠せますが、全部ではありません。リンクを使っていることと
  その時刻、タッチで何かが打たれたこと、パケットの数と各パケットの大きさの区分（たとえば大きなスマート
  カードの応答のおおよその大きさ）は分かります。打つのに2秒より長くかかると（キーの pacing 設定など）、
  その超えた分は見えます。名前や決まった UUID はアドバタイズしませんが、Bluetooth のアドレスは固定なので、
  電波の届く範囲に来るたびに同じ機器だと分かり、接続からはどの2台が組なのかも分かります。
- **キーの NFC。** 中継は、キーの NFC には何もしません。机の上に置いた YubiKey 5 NFC は、かざされた
  スマホに誰のものでも応答し、既定では NFC で Yubico OTP を渡します。NFC を使わないなら切っておいて
  ください。キーをパソコンに直接挿して `ykman config nfc --disable-all` を実行します（KeyRelay 越しでは
  ykman からキーが見えません）。
- **アテステーションと、組織の決まり。** 中継しても本物のキーのアテステーションがそのまま届くので、
  サービス側からは BLE 越しかどうか区別できません。自分のアカウントなら問題ありませんが、会社から
  支給されたキーなら、中継して使ってよいか確認してください。
- **キーのファームウェア。** YubiKey 5 シリーズのファームウェア 5.7 より前は、
  [YSA-2024-03](https://www.yubico.com/support/security-advisories/ysa-2024-03/)（EUCLEAK）の対象です。
  キーを手に入れて開け、高価な機材を使えば ECDSA の秘密鍵を取り出せます。開発に使ったキーは 5.1.2 です。
  危険は低いものの、机に置きっぱなしのキーはしばらく持ち出されやすく、YubiKey のファームウェアは
  更新できません。

## ペアリング用の鍵の作り方

自分のパソコンで作り、コミットしないでください（`*key*.bin` は `.gitignore` に入っています）。

```sh
(printf 'YDK1'; head -c 32 /dev/urandom) > keyrelay-key.bin
```

**全部の機器**（机上ユニットとそれぞれのレシーバー）の `0x190000` に同じファイルを書き込みます。鍵を
変えるときは、新しいファイルを作って全部の機器に書き込みます（守りを固めた機器は
[HARDENING.md](HARDENING.md) の「固めた機器を更新する」）。BLE のサービスの UUID も鍵で決まるので、
鍵の違う機器どうしは互いに見えもしません。

BLE のペアリング情報は `nvs` パーティションにあります。消えるのは、BOOT を3秒押したとき
（レシーバーは押している間に、机上ユニットは離したときに。机上ユニットの BOOT はケースの中）と、
まとめたイメージを `0x0` に書き込んだとき（`nvs` も上書きされる）です。ペアリング相手がいないか、
起動から120秒以内の机上ユニットは新しいペアリングを受け付けますが、KeyRelay の相互認証を通れるのは
PSK を持つ相手だけです。そのため、ペアリング情報を消しても、PSK を持っている機器は締め出せません
（「機器をなくしたり、盗まれたりしたら」参照）。
レシーバーは、机上ユニットのほうがペアリング情報を失っても、登録済みの机上ユニットのペアリング情報を残します
（「BLE の守り方」参照）。机上ユニットのペアリング情報を消したときは、レシーバーのほうも消してください。
机上ユニットの起動から120秒の間に、2台は自分でペアリングし直します。
